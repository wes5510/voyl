# Design Doc 작성 가이드

## 개요

### 목적

- 구현 전에 리스크를 파악하여 전체 비용을 줄인다
- 공유를 통해 PR 리뷰 품질과 속도를 높인다
- 의사결정 근거를 기록한다

### 작성자

- 담당 개발자 또는 프로젝트 리드

### 작성 시점

- 구현 시작 전
- 태스크 생성 전

### 작성 예외

다음의 경우 Design Doc을 생략할 수 있다.

- 단순 버그픽스 (원인이 명확하고 수정 범위가 좁은 경우)
- 스타일 수정 (색상, 여백, 폰트 등)
- 텍스트 수정 (오타, 문구 변경)
- 기존 패턴을 그대로 따르는 작업

## 파일명 컨벤션

- 형식: `YYYYMMDD-kebab-case-name.md`
- 예시: `20250104-timezone-support.md`

## 섹션별 가이드

**모든 섹션 필수.** 해당 내용이 없으면 "왜 없는지" 작성한다.

### Context (필수)

현재 상황과 문제를 정의한다.

**작성 원칙**

- 팩트 중심으로 작성
- 현재 상황 → 문제 정의 순서로 작성

**좋은 예시**

> 현재 예약 메시지 설정 화면에서 시간이 한국 시간(KST)으로만 표시된다.
> 해외 사용자는 자신의 로컬 시간을 직접 계산해야 하며, 잘못된 시간에 메시지가 발송되는 문제가 발생하고 있다.

**나쁜 예시**

> 타임존 기능이 필요하다.

→ 현재 상황과 문제가 없음

---

### Goals (필수)

이 프로젝트로 달성하려는 것을 작성한다.

**작성 원칙**

- 기능/범위 수준으로 작성
- 정량적/정성적 목표 모두 가능

**좋은 예시**

> - 사용자 로컬 타임존으로 예약 시간을 표시한다
> - 잘못된 시간 발송 CS 인입을 줄인다

**나쁜 예시**

> - 사용자 경험을 개선한다

→ 구체적이지 않음

---

### Non-goals (필수)

이번 프로젝트에서 하지 않는 것을 명시한다.

**작성 원칙**

- 기능/범위 수준으로 작성
- Non-goals가 없으면 "왜 없는지" 작성

**예시: Non-goals가 있는 경우**

> - 타임존 수동 선택 기능
> - 모바일 대응
> - 과거 예약 메시지 마이그레이션

**예시: Non-goals가 없는 경우**

> 이번 작업은 버그픽스로 범위가 명확하여 제외할 사항이 없다.

---

### What changes (필수)

무엇이 변경되는지 작성한다.

**작성 원칙**

- 개발 지식 없이 이해할 수 있는 수준으로 작성
- 다른 자료 참고 없이 변경 범위를 파악할 수 있도록 작성
- UI/UX, 인터랙션, 로직, 구조 등 해당하는 것 모두 포함
- **AS-IS/TO-BE 구조로 작성** (변경 대상별로 구분)

**구조**

```markdown
### {변경 대상}

#### AS-IS
- 현재 동작/구조

#### TO-BE
- 변경 후 동작/구조
```

- AS-IS: 기존 동작이 있는 경우 작성. 없으면 "왜 없는지" 작성
- TO-BE: 변경 후 동작/구조
- 변경 대상 예시: 페이지, 컴포넌트, 레이어, 모델, 데이터 흐름

**좋은 예시**

> ### 예약 설정 화면
>
> #### AS-IS
> - 시간이 한국 시간(KST)으로만 표시
> - 해외 사용자는 시간 계산 필요
>
> #### TO-BE
> - 사용자 로컬 타임존으로 시간 표시
> - 타임존 선택 드롭다운 추가
>
> ### 예약 목록
>
> #### TO-BE
> - 저장된 예약도 로컬 시간으로 표시

**나쁜 예시**

> - 타임존 관련 UI 수정

→ 구체적이지 않음, AS-IS/TO-BE 구분 없음

---

### Design (필수)

기술적 접근 방법을 설명한다.

**작성 원칙**

- 해당하는 영역만 작성 (Main, Renderer, 또는 둘 다)
- 레이어별 구조와 관계를 설명한다
- 데이터 흐름을 설명한다
- 코드는 작성하지 않는다 (필요시 수도코드만)
- 해당 영역이 없으면 "왜 없는지" 작성

**포함할 내용**

| 영역 | 항목 |
|------|------|
| Main | IPC 설계, 레이어 구조 (ipc/model/repo), 데이터 모델, 데이터 흐름 |
| Renderer | 레이어 구조 (page/state/repo/model), 상태 관리, 데이터 흐름, 컴포넌트 구조 |

**예시: Main + Renderer 모두 변경**

> ### Main
>
> **IPC 설계**
> ```
> channel: 'schedule:create'
> - 요청: { time: string, timezone: string }
> - 응답: Schedule
> ```
>
> **레이어 구조**
> - ipc: ScheduleHandler
> - model: ScheduleService
> - repo: ScheduleRepository
>
> **데이터 흐름**
> - IPC 요청 → model 검증 → repo 저장 → 응답
>
> ### Renderer
>
> **레이어 구조**
> - page: SchedulePage
> - state: useScheduleStore (Valtio)
> - repo: useScheduleQuery (React Query)
>
> **컴포넌트 구조**
> - TimezoneSelector: 신규
> - ScheduleForm: 기존 + TimezoneSelector 추가

**예시: Renderer만 변경**

> ### Main
>
> 해당 없음. IPC 변경 없이 기존 API 사용.
>
> ### Renderer
>
> **컴포넌트 구조**
> - ScheduleList: 표시 로직만 수정

### Alternatives considered (필수)

검토한 대안과 선택하지 않은 이유를 작성한다.

**작성 원칙**

- 최소 1개 이상의 대안을 검토한다
- 각 대안의 장단점을 명시한다
- 대안이 없으면 "왜 없는지" 작성
- **성능, 보안 등 기술적 고려사항도 대안 비교 시 포함**

**기술적 고려사항 참고 항목**

대안 비교 시 다음 항목을 고려한다:

- 성능: 쿼리 성능, 렌더링, 번들 사이즈
- 보안: 파일 접근 권한, 입력 검증, XSS
- 확장성: 데이터 증가 대응
- 마이그레이션: 스키마 변경 시 기존 데이터 처리
- 에러 처리: 실패 시 동작, 롤백, 사용자 피드백
- 접근성: 키보드 네비게이션, 스크린리더

**예시: 대안이 있는 경우**

> **대안 1: 파일시스템만 사용 (SQLite 미사용)**
> - 장점: 구현 단순화
> - 단점: 쿼리 성능 저하, 필터링 어려움
> - 선택하지 않은 이유: 목록 조회 시 성능 문제 예상
>
> **대안 2: 타임존을 time 필드에 포함 (ISO 8601)**
> - 장점: 스키마 변경 없음
> - 단점: 기존 데이터와 호환성 문제
> - 선택하지 않은 이유: 마이그레이션 복잡도

**예시: 대안이 없는 경우**

> 기존 패턴을 따르는 작업으로, 다른 접근 방식이 없다.

---

### References (필수)

관련 자료 링크를 첨부한다.

**예시: 참조가 있는 경우**

> - [피그마 디자인](링크)
> - [사용자 리서치 결과](링크)
> - [관련 CS 인입 현황](링크)

**예시: 참조가 없는 경우**

> 관련 외부 자료 없음. 코드베이스 내 기존 패턴 참조.

## 작업 유형별 가이드

### 기능 개발

전체 섹션을 충실히 작성한다.

### 리팩토링

- Context: 현재 코드의 문제점
- Non-goals: "기능 변경 없음" 명시
- Alternatives considered: "기존 코드 유지 vs 선택한 방식" 비교

### 인프라 작업

- Context: 현재 인프라 상황
- Alternatives considered: 빌드 시간, 호환성 등 기술적 고려사항 포함

---

## 리뷰 체크리스트

리뷰어는 다음을 확인한다.

### Context & Goals

- [ ] 문제 정의가 명확한가
- [ ] 목표가 구체적인가

### Design

- [ ] 구조가 명확하게 설명되어 있는가
- [ ] 데이터 흐름이 이해되는가
- [ ] 더 나은 방법이 있는가

### Alternatives considered

- [ ] 대안이 검토되었는가 (또는 없는 이유가 타당한가)
- [ ] 선택하지 않은 이유가 타당한가
- [ ] 기술적 고려사항(성능, 보안 등)이 대안 비교에 반영되었는가
