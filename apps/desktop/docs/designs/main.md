# Design Doc - Main Process 작성 가이드

## 개요

### 목적
- 기술적 접근 방법을 문서화하여 리스크를 조기에 발견한다
- 대안 검토 과정을 기록하여 의사결정 근거를 남긴다
- IPC 인터페이스를 정의하여 Renderer와 협업한다

### 작성자
- 담당 개발자

### Main-Renderer 협업
- IPC 변경이 있는 경우, Main Process Design Doc을 먼저 작성하거나 IPC 설계를 먼저 합의한다
- Renderer는 Main Design Doc의 IPC 설계를 참조한다

### 작성 예외
다음의 경우 Design Doc을 생략할 수 있다.
- 단순 CRUD (예: 필드 추가, 기존 패턴과 동일한 작업)
- 기존 패턴 그대로 따르는 작업
- 기술적 의사결정이 없는 작업

## 섹션별 가이드

### Design (필수)
기술적 접근 방법을 설명한다.

**왜 필요한가**
- 구현 전에 구조적 문제를 발견할 수 있다
- 리뷰어가 더 나은 방법을 제안할 수 있다
- Renderer 개발자가 IPC를 미리 파악할 수 있다

**작성 원칙**
- 레이어별 구조와 관계를 설명한다
- 데이터 흐름을 설명한다
- 코드는 작성하지 않는다 (필요시 수도코드만)
- 필요시 다이어그램을 추가한다

**포함할 내용**
- IPC 설계 (채널, 요청/응답 구조)
- 레이어 구조 (repo, model, ipc)
- 데이터 모델 (스키마 변경이 있는 경우)
- 데이터 흐름 (IPC 요청 → model → repo → 응답)
- 파일시스템/SQLite 영향

**미포함**
- 함수 내부 구현
- 쿼리문 상세
- 에러 코드 전체 목록

**좋은 예시**
> **IPC 설계**
> ```
> channel: 'schedule:list'
> - 요청: { filter?: ScheduleFilter }
> - 응답: Schedule[]
>
> channel: 'schedule:create'
> - 요청: { time: string (UTC), timezone: string }
> - 응답: Schedule
> - 변경: timezone 필드 추가 (선택, 기본값 UTC)
> ```
>
> **레이어 구조**
> - ipc: ScheduleHandler - IPC 채널 처리
> - model: ScheduleService - 비즈니스 로직
> - repo: ScheduleRepository - 파일시스템 + SQLite 접근
>
> **데이터 모델**
> - schedules 테이블: timezone 컬럼 추가 (VARCHAR, nullable)
>
> **데이터 흐름**
> - 저장: IPC 요청 → model 검증 → repo 저장 → IPC 응답
> - 조회: IPC 요청 → model 처리 → repo 조회 → IPC 응답

**나쁜 예시**
> SQLite에 저장하고 IPC로 반환한다.

→ 구조, IPC 설계, 데이터 흐름이 없음

### Alternatives considered (필수)
검토한 대안과 선택하지 않은 이유를 작성한다.

**왜 필요한가**
- "이 방법은 안 되나요?" 질문을 미리 차단
- 의사결정 근거를 남긴다

**작성 원칙**
- 최소 1개 이상의 대안을 검토한다
- 각 대안의 장단점을 명시한다
- 선택하지 않은 이유를 명시한다

**좋은 예시**
> **대안 1: 파일시스템만 사용 (SQLite 미사용)**
> - 장점: 구현 단순화
> - 단점: 쿼리 성능 저하, 필터링 어려움
> - 선택하지 않은 이유: 목록 조회 시 성능 문제 예상
>
> **대안 2: 타임존을 time 필드에 포함 (ISO 8601)**
> - 장점: 스키마 변경 없음
> - 단점: 기존 데이터와 호환성 문제
> - 선택하지 않은 이유: 마이그레이션 복잡도

---

### Cross-cutting concerns (필수)
성능, 보안 등 고려사항을 작성한다.

**왜 필요한가**
- 기능 외적인 문제를 조기에 발견한다
- 리뷰 시 체크포인트가 된다

**작성 원칙**
- 성능은 항상 고려한다
- 나머지는 프로젝트에 따라 선택적으로 작성한다

**체크리스트**
- 성능 (필수): 쿼리 성능, 인덱스, 캐싱
- 보안: 파일 접근 권한, 입력 검증
- 확장성: 데이터 증가 대응
- 마이그레이션: 스키마 변경 시 기존 데이터 처리
- 에러 처리: 실패 시 동작, 롤백

**좋은 예시**
> **성능**
> - timezone 컬럼 추가 → 기존 쿼리 영향 없음
> - 인덱스 추가 불필요
>
> **마이그레이션**
> - 기존 데이터: timezone = null (UTC로 간주)
> - 하위 호환성 유지
