# Design Doc - Renderer Process 작성 가이드

## 개요

### 목적
- 기술적 접근 방법을 문서화하여 리스크를 조기에 발견한다
- 대안 검토 과정을 기록하여 의사결정 근거를 남긴다

### 작성자
- 담당 개발자

### Main-Renderer 협업
- IPC 변경이 있는 경우, Main Process Design Doc을 먼저 작성하거나 IPC 설계를 먼저 합의한다
- Renderer는 Main Design Doc의 IPC 설계를 참조한다

### 작성 예외
다음의 경우 Design Doc을 생략할 수 있다.
- 단순 UI 수정 (예: 버튼 색상 변경, 텍스트 수정, 여백 조정)
- 기존 패턴 그대로 따르는 작업 (예: 기존 CRUD 페이지와 동일한 구조의 신규 페이지)
- 기술적 의사결정이 없는 작업 (예: 디자인 시안 그대로 구현, 기존 컴포넌트 조합만으로 완성)

## 섹션별 가이드

### Design (필수)
기술적 접근 방법을 설명한다.

**왜 필요한가**
- 구현 전에 구조적 문제를 발견할 수 있다
- 리뷰어가 더 나은 방법을 제안할 수 있다

**작성 원칙**
- 레이어별 구조와 관계를 설명한다
- 상태 관리 방식과 데이터 흐름을 설명한다
- 재사용할 것과 새로 만들 것을 구분한다
- 코드는 작성하지 않는다 (필요시 수도코드만)
- 필요시 다이어그램을 추가한다

**포함할 내용**
- 레이어 구조 (page, state, repo, model)
- 상태 관리 (React Query + Valtio 활용 방식)
- 데이터 흐름 (IPC → state → UI)
- 재사용 여부 (기존 컴포넌트/훅 활용 vs 신규 생성)
- 사용할 라이브러리 (새로 도입하는 경우)

**미포함**
- 컴포넌트 내부 구현
- 함수/훅 시그니처 상세
- CSS/스타일 상세

**좋은 예시**
> **레이어 구조**
> - page: SchedulePage - 예약 관리 페이지
> - state: useScheduleStore (Valtio) - 로컬 UI 상태
> - repo: useScheduleQuery (React Query) - IPC 통신
> - model: Schedule 타입 정의
>
> **상태 관리**
> - 서버 상태: React Query로 관리 (캐싱, 자동 리페치)
> - UI 상태: Valtio store로 관리 (선택된 항목, 필터 등)
>
> **데이터 흐름**
> - 저장 시: UI 입력 → mutation → IPC → 캐시 무효화 → 리렌더링
> - 표시 시: IPC 응답 → React Query 캐시 → UI 렌더링
>
> **컴포넌트 구조**
> - TimezoneSelector: 타임존 선택 드롭다운 (신규)
> - ScheduleForm: 기존 컴포넌트에 TimezoneSelector 추가
> - ScheduleList: 기존 컴포넌트, 표시 로직만 수정
>
> **라이브러리**
> - 타임존 변환: Intl.DateTimeFormat (네이티브 API 사용, 추가 라이브러리 없음)

**나쁜 예시**
> React Query 사용해서 구현한다.

→ 구조, 상태 관리, 데이터 흐름이 없음

### Alternatives considered (필수)
검토한 대안과 선택하지 않은 이유를 작성한다.

**왜 필요한가**
- "이 방법은 안 되나요?" 질문을 미리 차단
- 의사결정 근거를 남긴다

**작성 원칙**
- 최소 1개 이상의 대안을 검토한다
- 각 대안의 장단점을 명시한다
- 선택하지 않은 이유를 명시한다

**좋은 예시**
> **대안 1: date-fns-tz 라이브러리 사용**
> - 장점: 풍부한 기능, 익숙한 API
> - 단점: 번들 사이즈 증가 (~15KB)
> - 선택하지 않은 이유: 단순 변환만 필요하여 네이티브 API로 충분
>
> **대안 2: Main Process에서 변환 후 전달**
> - 장점: Renderer 로직 단순화
> - 단점: 사용자 타임존을 Main에서 관리해야 함
> - 선택하지 않은 이유: 기존 IPC 구조 변경 필요, 복잡도 증가

**나쁜 예시**
> 다른 방법은 없다.

→ 대안 검토 없음

---

### Cross-cutting concerns (필수)
성능, 보안, 접근성 등 고려사항을 작성한다.

**왜 필요한가**
- 기능 외적인 문제를 조기에 발견한다
- 리뷰 시 체크포인트가 된다

**작성 원칙**
- 성능은 항상 고려한다
- 나머지는 프로젝트에 따라 선택적으로 작성한다

**체크리스트**
- 성능 (필수): 렌더링, 번들 사이즈, IPC 호출 횟수
- 접근성: 키보드 네비게이션, 스크린리더
- 보안: XSS, 민감 정보 노출
- 에러 처리: 실패 시 동작, 사용자 피드백

**좋은 예시**
> **성능**
> - 타임존 변환은 렌더링 시 매번 호출됨 → useMemo로 최적화
> - 추가 라이브러리 없음 → 번들 사이즈 영향 없음
>
> **접근성**
> - TimezoneSelector: 키보드로 선택 가능하도록 구현
