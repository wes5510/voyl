# Tech Spec 작성 가이드

## 개요

### 목적
- 프로젝트 초기에 리스크를 파악하여 전체 비용을 줄인다
- 공유를 통해 PR 리뷰 품질과 속도를 높인다
- 집단 지성을 활용한다

### 작성자
- 담당 개발자 또는 프로젝트 리드

### 작성 시점
- 구현 시작 전
- Design Doc 작성 전

### Design Doc과의 관계
- Tech Spec: 무엇을 하는지 (What)
- Design Doc: 어떻게 하는지 (How)
- Tech Spec 리뷰 완료 후 Design Doc 작성

### 작성 예외
다음의 경우 Tech Spec을 생략할 수 있다.
- 소규모 버그픽스
- 리팩토링 (기존 기능 명세는 이미 존재해야 함)
- 단순 의존성 업데이트

---

## 섹션별 가이드

### Context (필수)
현재 상황과 문제를 정의한다.

**왜 필요한가**
- 리뷰어가 배경을 빠르게 파악할 수 있다
- 문제 정의가 잘못되면 초기에 수정할 수 있다

**작성 원칙**
- 팩트 중심으로 작성
- 현재 상황 → 문제 정의 순서로 작성

**좋은 예시**
> 현재 예약 메시지 설정 화면에서 시간이 한국 시간(KST)으로만 표시된다.
> 해외 사용자는 자신의 로컬 시간을 직접 계산해야 하며, 잘못된 시간에 메시지가 발송되는 문제가 발생하고 있다.

**나쁜 예시**
> 타임존 기능이 필요하다.

→ 현재 상황과 문제가 없음

---

### Goals (필수)
이 프로젝트로 달성하려는 것을 작성한다.

**왜 필요한가**
- 리뷰어가 PR 리뷰 시 중점으로 봐야 할 것을 알 수 있다
- 더 나은 방법을 제안할 수 있다

**작성 원칙**
- 기능/범위 수준으로 작성
- 정량적/정성적 목표 모두 가능

**좋은 예시**
> - 사용자 로컬 타임존으로 예약 시간을 표시한다
> - 잘못된 시간 발송 CS 인입을 줄인다

**나쁜 예시**
> - 사용자 경험을 개선한다

→ 구체적이지 않음

---

### Non-goals (권장)
이번 프로젝트에서 하지 않는 것을 명시한다.

**왜 필요한가**
- 리뷰어가 "이것도 해야 하지 않나요?" 질문을 미리 차단
- 스코프 논쟁 최소화

**작성 원칙**
- 기능/범위 수준으로 작성

**좋은 예시**
> - 타임존 수동 선택 기능
> - 모바일 대응
> - 과거 예약 메시지 마이그레이션

---

### What changes (필수)
무엇이 변경되는지 작성한다.

**왜 필요한가**
- 변경 범위를 한눈에 파악할 수 있다
- 다른 작업과 겹치는 부분을 발견할 수 있다

**작성 원칙**
- 개발 지식 없이 이해할 수 있는 수준으로 작성
- 다른 자료 참고 없이 변경 범위를 파악할 수 있도록 작성
- UI/UX, 인터랙션, 로직, 구조 등 해당하는 것 모두 포함

**좋은 예시**
> - 예약 설정 화면에 사용자 타임존 표시 추가
> - 시간 선택 시 로컬 시간 기준으로 동작
> - 저장된 예약 목록에서도 로컬 시간으로 표시

**나쁜 예시**
> - 타임존 관련 UI 수정

→ 구체적이지 않음

---

### References (권장)
관련 자료 링크를 첨부한다.

**예시**
> - [피그마 디자인](링크)
> - [사용자 리서치 결과](링크)
> - [관련 CS 인입 현황](링크)
